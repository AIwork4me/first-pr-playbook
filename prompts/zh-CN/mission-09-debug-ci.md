# Mission 09｜CI 根因排查

[第 09 课](../../lessons/zh-CN/09-debug-ci.md) · [模板：CI 排查记录](../../templates/zh-CN/ci-triage.md) · [English version](../en/mission-09-debug-ci.md)

**任务.** 依据日志与对照（而不是红色图标），把 PR 上每个异常 CI Job 归入正确类别：代码 / 格式 / 测试 / 权限 / 基础设施 / base 已有 / 未知。

**背景.** 红色 CI 的含义是「一个需要解释的失败」。错误归因浪费维护者时间；正确归因赢得信任。

**输入.** PR URL 与当前 HEAD SHA；Checks 页与日志访问权；（可选）base 分支。

**约束.**

- 读失败 Step 的日志；引用第一条有意义的错误行；保存运行 URL。
- 状态词含义不同：`failed`、`action_required`、`cancelled`、`pending`。`action_required` 是权限门槛，绝不是测试失败。
- 宣称「base 已有」必须有可比的 base 分支（或维护者引用的）运行作为证据。
- 每个 Job 只给一条最小建议动作；重跑和评论由人类决定。
- 绝不把未完成的工作流写成绿色。

**步骤.**

1. 枚举当前 HEAD 的全部异常 Job 及 URL。
2. 每个 Job：失败 Step、关键日志行、可比运行证据、类别、最小下一步。
3. 可本地复现的（格式检查）用仓库固定版本工具复现。
4. 填写[CI 排查记录](../../templates/zh-CN/ci-triage.md)，提出人类的下一步动作。

**验证.** 至少一个异常 Job 被端到端解释并有证据；每个类别主张都附支撑日志或对照。

**交付.** 一份有证据的 CI 异常归因记录。

**停止条件.** 日志无法区分类别时停在 UNKNOWN——记录检查过什么。没有假设就不要反复重跑；绝不把「重跑通过」当作根因已解决的证明。
